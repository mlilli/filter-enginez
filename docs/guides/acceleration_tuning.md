# Guide — Tuning the acceleration stack

> **Audience:** consumers whose filtering is slower than they expected, or who want to know what the five `acceleration`
> toggles buy before touching them. Every number here comes from [`benchmarks/RESULTS.md`](../../benchmarks/RESULTS.md),
> generated by `pnpm bench:write` on 2026-10-15 over the synthetic wine tiers: the 10k figures are the first 10,000
> generated wines and the 150k figures the 150,000-wine full tier.

---

## First: are the bitmaps running?

The Roaring-Bitmap path is WASM-backed, and **it engages only after you have awaited its initializer.** Before that,
`shouldUseBitmap()` returns `false` and every path — results, `computeResults()`, `simulate()` — uses the per-item
predicate evaluator.

```ts
import { createFilterEngine, initializeBitmapAcceleration } from '@filter-enginez/core';
import { type Wine, wines } from '@filter-enginez/mock-data/wine';

await initializeBitmapAcceleration(); // once, at app startup
const engine = createFilterEngine<Wine>({ sourceData: wines });
```

**Skipping it changes speed, never answers.** Results are identical either way; without the bitmaps the filter
intersection measured here runs 42.1× slower at 10k items (`filter-intersection`), and uncached `simulate()` about 2.8×
slower (`simulate-per-option`). The readiness gate exists so an app whose WASM asset is still in flight on the first
ticks of page load keeps working rather than throwing; there is no warning when the init is missing, so check for it:

```ts
import { isBitmapAccelerationReady } from '@filter-enginez/core';

if (!isBitmapAccelerationReady()) {
  // Nothing below this line will be accelerated.
}
```

The gate applies to `bitmap: 'on'` as well as `'auto'`: asking for `'on'` explicitly does not bypass it.

## The five toggles

All live under `acceleration` on `createFilterEngine`, each with a working default:

```ts
import { createFilterEngine } from '@filter-enginez/core';
import { type Wine, wines } from '@filter-enginez/mock-data/wine';

const engine = createFilterEngine<Wine>({
  sourceData: wines,
  acceleration: {
    bitmap: 'auto', // 'auto' | 'on' | 'off'
    exclusionGraph: 'lazy', // 'lazy' | 'eager' | 'off'
    simulationCache: true, // boolean
    spatialIndex: 'auto', // 'auto' | 'off'
    textIndex: 'auto', // 'auto' | 'on' | 'off'
  },
});
```

The defaults above are what you get by passing nothing. **The `'off'` settings exist mainly so the benchmark matrix can
isolate one layer at a time** — they are a measurement tool more than a tuning knob, and the table below is the reason.
The layers are not fully independent: `spatialIndex` and `textIndex` serve the bitmap build, and the exclusion graph is
built from bitmaps, so `bitmap: 'off'` turns those three off too (see the last section).

---

## What each layer is worth, measured

| Layer             | Workload                                 | Off → On, 10k | Off → On, 150k |
| ----------------- | ---------------------------------------- | ------------- | -------------- |
| `bitmap`          | filter intersection                      | **42.1×**     | **37.0×**      |
| `spatialIndex`    | geo radius query                         | **298.5×**    | **290.9×**     |
| `textIndex`       | text search, `'allWords'`                | **448.5×**    | **402.4×**     |
| `textIndex`       | fuzzy search, threshold 0.2              | **2.7×**      | **2.5×**       |
| `textIndex`       | fuzzy search, threshold 0.4              | 1.0×          | 1.0×           |
| `simulationCache` | simulate-per-option                      | **114.5×**    | **2819.2×**    |
| `exclusionGraph`  | simulate-per-option, bitmaps on, no memo | 1.0×          | 1.0×           |

Three of those rows deserve a closer look.

### `simulationCache` matters most, and it is on by default

114.5× at 10k, **2819.2× at 150k** — and it scales that way because the memo turns an O(items × rules) projection into a
map lookup. The absolute numbers make the point better than the ratios: with the cache on, simulate-per-option is
**0.086 ms at 150k**, essentially flat from its 0.087 ms at 10k. With it off, 150k costs **241 ms**, about fourteen
frames at 60 Hz for one hover. Keep it on outside a benchmark.

The cache is a fixed-size LRU of **100** results, each carrying a **5**-item preview sample (`SimulationResult.sample`);
`acceleration.simulationCache` switches it on or off and does not resize it. Every state change clears it, so 100 is the
number of distinct hypotheticals a UI can ask about between two filter changes before older answers are recomputed.

### `exclusionGraph` pays off in direct queries, not in `simulate()`

In the simulate benchmark the graph reads 1.0× (9.91 ms lazy against 9.80 ms off at 10k). That is the expected reading:
`simulate()` consults the graph only once it is built, and `'lazy'` builds it only when something queries it directly,
so a pure simulate workload never builds it. Where the graph pays is its O(1) direct queries —
`engine.exclusionGraph.areExclusive(a, b)` and `getExclusions(id)` — for "grey out the filters incompatible with this
one".

`'eager'` keeps the graph built: the engine rebuilds it after construction and after every rule or data change, which
moves the build cost onto each filter change and makes the `simulate()` short-circuit available.
`engine.precomputeExclusions()` builds it once, on demand — call it in idle time after data load if the first direct
query feels slow.

### `textIndex` is worth 400× for `allWords` and nothing for a loose fuzzy threshold

The two fuzzy rows are the interesting pair. At threshold **0.2** the index is worth 2.7× at 10k and 2.5× at 150k; at
**0.4** it is worth 1.0× — the means sit within 0.6% of each other, index on or off, at both sizes.

That is the trigram bound proving nothing. The index prunes fuzzy candidates by a _sound_ lower bound on trigram overlap
before the exact Fuse confirm, and at a loose threshold the bound is zero, so the query plan bypasses the index and runs
the same scan as `'off'`: one Fuse search over the whole collection, its index built once per collection and reused for
every later query. That row is the guardrail that the bypass costs nothing: about 271 ms at 150k is the cost of a loose
fuzzy search however you index it, and the setting that changes it is the threshold.

Substring and `'tokenized'` text matching are **never** index-served, by design — native `String.includes` already wins.
Only `TextSearchRule` in case-insensitive `'allWords'` mode and `FuzzySearchRule` consult the index, and a fuzzy rule
bypasses it whenever its options change what the query means (`ignoreDiacritics`, `useExtendedSearch`, `useTokenSearch`)
or it searches several `keys`.

## The `'auto'` thresholds

Both `bitmap: 'auto'` and `textIndex: 'auto'` gate on source-data size, at **500 items**. Both constants are exported
from `@filter-enginez/core`:

| Constant                    | Value | Gates                               |
| --------------------------- | ----- | ----------------------------------- |
| `AUTO_BITMAP_THRESHOLD`     | 500   | the whole bitmap path in `'auto'`   |
| `TEXT_INDEX_AUTO_THRESHOLD` | 500   | the inverted text index in `'auto'` |

Below 500, building a rule's bitmap costs one full predicate pass — exactly the work the bitmap was going to save — so a
one-shot query is no faster and a cold query is slower. Above it, the bitmap path wins.

**`textIndex: 'on'` is the one override with a clear use case.** A _cold_ posting build costs about as much as one
predicate scan, but a _warm_ query is nearly flat while the scan grows linearly — so the index wins from the **second**
query. If your workload is repeated text queries over a few hundred items — a type-ahead over a small corpus — set
`textIndex: 'on'` **and** `bitmap: 'on'`: the index serves the bitmap build, so below 500 items it engages only when the
bitmaps do.

## Measuring instead of guessing

`engine.computeResults()` recomputes the result indices on every call — the bitmap AND-chain when bitmaps are engaged,
otherwise a copy of the predicate answer — and returns a `Uint32Array` equal to `getResultIndices()`. Unlike
`getResultIndices()`, a memoized signal that hands back a cached array until the next change, it is what to time if you
want to measure the filter rather than a cache hit.

```ts
import type { FilterEngine } from '@filter-enginez/core';
import type { Wine } from '@filter-enginez/mock-data/wine';

declare const engine: FilterEngine<Wine>;

const t0 = performance.now();
const indices = engine.computeResults();
const elapsed = performance.now() - t0;
```

Two things that will mislead you if you time the wrong one:

- **`getResultIndices()` on an unchanged engine is a cache read.** Timing it measures the memo, not the filter.
- **The first `computeResults()` after a source-data change includes the lazy bitmap builds** for every active rule, one
  `O(items)` pass each. That cold cost is real and worth knowing, but it is not the steady-state number — take the
  second measurement.

## When the bitmap path steps aside

**The bitmap path serves conjunctions over the full source data.** It is a bitwise AND across the active rules' bitmaps,
which is exactly "every rule must pass". So it steps aside — and the predicate evaluator answers, with identical results
— when:

- an expression is set (`engine.setExpression(...)` with OR / NOT composition),
- a filter group with `composition: 'or'` spans two or more registered rules, or
- `setWorkingSet(...)` has narrowed the working set (bitmaps index the source data).

Flat rules and `'and'` groups AND together; anything else is evaluated per item.

Two layers are **inert** rather than slow when the bitmap path is off, because both serve the bitmap build:
`spatialIndex` and `textIndex`. The exclusion graph is built from bitmaps too. So `bitmap: 'off'` turns all three off
regardless of their own toggles — it is the off switch for the whole stack except the simulation cache.

---

## Checklist

- [ ] `await initializeBitmapAcceleration()` at startup — the one that is silent when missed
- [ ] Leave the five defaults alone unless a measurement says otherwise
- [ ] `simulationCache: true` always, outside a benchmark
- [ ] `textIndex: 'on'` plus `bitmap: 'on'` if you have repeated text queries under 500 items
- [ ] `exclusionGraph: 'eager'` or `precomputeExclusions()` if you use the graph's direct queries
- [ ] Time `computeResults()`, not `getResultIndices()`, and discard the first call
- [ ] Expect the predicate path in expression mode, with `'or'` groups, and over a narrowed working set
